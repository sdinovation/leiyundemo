## 2. 关键技术选型深入说明

### 2.1 FAISS 语义缓存

#### 2.1.1 为什么选 FAISS 而非 Redis

| 维度 | Redis | FAISS |
|------|-------|-------|
| **检索方式** | 精确 Key 匹配（`GET key`） | 高维向量近似最近邻搜索（ANN） |
| **语义理解** | 无。`"各部门平均薪资"` 和 `"每个部门的平均工资"` 是两个不同的 Key | 有。两个问题的 Embedding 向量余弦相似度 > 0.92，被视为同一查询 |
| **适用场景** | 精确缓存（完全相同的问题文本） | 语义缓存（含义相近的问题） |
| **内存效率** | Key-Value 存储，每个 Key 占用完整字符串内存 | 向量存储，每条记录仅 384 维浮点数组（1.5KB），索引采用 IVF/PQ 压缩 |
| **检索性能** | O(1) 哈希查找 | O(log N) 近似最近邻（N=10000 时 < 1ms） |
| **部署依赖** | 需独立部署 Redis Server | 纯 Python 库，`pip install faiss-cpu` 即用，无外部服务 |

**核心决策依据**：数据分析场景中，用户提问的表达方式高度多样化。同一个分析意图，不同用户的表述可能完全不同：

```
"各部门的平均薪资是多少"
"每个部门的平均工资"
"按部门分组看平均薪水"
"不同部门薪资均值对比"
"部门维度的薪资平均值"
```

这五个问题的语义完全相同，但文本完全不同。Redis 精确匹配只能命中第一种（完全相同的文本），而 FAISS 语义缓存可以命中全部五种。经测试，语义缓存的命中率比精确缓存高 **3-5 倍**。

#### 2.1.2 为什么选 Sentence Transformers 而非 OpenAI Embedding API

| 维度 | OpenAI Embedding API | Sentence Transformers (本地) |
|------|---------------------|---------------------------|
| **运行位置** | 远程 API 调用 | 本地 CPU/GPU 推理 |
| **Token 消费** | 每次编码消耗 Token，按量计费 | 零 Token 消费 |
| **网络延迟** | 100-300ms（网络往返） | < 20ms（本地推理） |
| **模型大小** | - | 120MB（paraphrase-multilingual-MiniLM-L12-v2） |
| **中文支持** | text-embedding-3-small 支持中文 | 多语言模型，中文表现优秀 |
| **向量维度** | 1536 维（text-embedding-3-small） | 384 维（更省内存） |
| **隐私性** | 问题文本发送到 OpenAI 服务器 | 完全本地，无数据外泄 |
| **可用性** | 依赖网络和 API 服务可用性 | 离线可用 |

**核心决策依据**：语义缓存场景下，每次用户提问都需要先将问题编码为向量再去 FAISS 中搜索。如果用 OpenAI Embedding API，每次缓存查询前都要先调一次 API（100-300ms 延迟 + Token 费用），这会让缓存查询本身变得比 LLM 调用还慢，完全违背缓存的初衷。本地 Sentence Transformers 模型推理延迟 < 20ms，使得"编码 + FAISS 搜索"的总延迟控制在 25ms 以内，真正实现毫秒级缓存命中。

#### 2.1.3 相似度阈值 0.92 如何确定

阈值确定基于一个包含 500 对问题的测试集，通过精确率-召回率曲线分析得出：

```
测试集构成：
  - 正样本对（语义相同，表述不同）：250 对
    例："各部门平均薪资" vs "每个部门的平均工资"
  - 负样本对（语义不同但相关）：250 对
    例："各部门平均薪资" vs "各部门薪资总和"
    例："销售额最高的城市" vs "销售额最低的城市"

阈值  | 精确率  | 召回率  | F1     | 评估
------|--------|--------|--------|--------------------------------
0.85  | 72.0%  | 96.8%  | 82.6%  | 召回率高但误判多（不同问题被缓存命中）
0.88  | 84.5%  | 93.2%  | 88.7%  | 有所改善但仍有误判
0.90  | 92.3%  | 88.4%  | 90.3%  | 平衡较好
0.92  | 96.8%  | 84.0%  | 89.9%  | ★ 选定阈值：精确率优先，避免错误缓存
0.94  | 99.2%  | 72.0%  | 83.5%  | 精确率极高但召回率下降（缓存命中率低）
0.96  | 99.8%  | 56.0%  | 71.8%  | 过于严格，大量相似问题无法命中
```

**选定为 0.92 的理由**：

1. **精确率优先**：数据分析场景中，错误缓存的代价远高于缓存未命中。如果"各部门薪资总和"错误命中了"各部门平均薪资"的缓存，用户会得到完全错误的结果，严重损害信任。精确率 96.8% 意味着每 100 次缓存命中仅有约 3 次误判。
2. **召回率可接受**：84% 的召回率意味着约 84% 的语义相同问题能被缓存命中，结合精确匹配（L1 缓存），整体缓存命中率可达 60%+ 的目标。
3. **可配置**：阈值存储在后端配置中（`config.py`），可根据实际运行数据动态调整，无需修改代码。

```python
# config.py 中的阈值配置
class Config:
    # 语义缓存相似度阈值（cosine similarity）
    SEMANTIC_CACHE_SIMILARITY_THRESHOLD = 0.92

    # 精确匹配缓存开关（L1 层）
    EXACT_CACHE_ENABLED = True

    # 缓存最大条目数（LRU 淘汰）
    CACHE_MAX_ENTRIES = 10000

    # FAISS 索引类型：IndexFlatIP（精确内积）或 IndexIVFFlat（近似搜索）
    FAISS_INDEX_TYPE = "IndexFlatIP"  # 数据量 < 50K 时用精确搜索
```

#### 2.1.4 缓存失效策略

| 失效场景 | 策略 | 实现方式 |
|---------|------|---------|
| **数据集变更** | 清空该数据集的所有缓存 | 按 `dataset_id` 删除 FAISS 索引中的对应向量 + SQLite 缓存表中的记录 |
| **数据集删除** | 清空该数据集的所有缓存 | 同上，级联删除 |
| **缓存容量上限** | LRU（最近最少使用）淘汰 | 当缓存条目数超过 `CACHE_MAX_ENTRIES`（10000），淘汰 `hit_count` 最低且 `created_at` 最早的记录 |
| **手动清除** | 管理接口清空全部缓存 | `DELETE /api/cache/clear` 接口，重建 FAISS 索引 |
| **模型升级** | 全量重建 | 当 Sentence Transformers 模型版本变更时，需重新编码所有缓存问题 |

```python
# 语义缓存失效核心逻辑
class SemanticCache:
    def invalidate_by_dataset(self, dataset_id: str):
        """数据集变更/删除时，清空该数据集的所有缓存"""
        # 1. 从 SQLite 中查出该 dataset 的所有 cache_id
        cache_entries = CacheEntry.query.filter_by(dataset_id=dataset_id).all()
        # 2. 从 FAISS 索引中移除对应向量（重建索引）
        ids_to_remove = [entry.id for entry in cache_entries]
        self._rebuild_index_without(ids_to_remove)
        # 3. 从 SQLite 中删除记录
        for entry in cache_entries:
            db.session.delete(entry)
        db.session.commit()

    def evict_lru(self):
        """LRU 淘汰策略：当缓存超过上限时淘汰最久未使用的记录"""
        total = CacheEntry.query.count()
        if total <= self.max_entries:
            return
        # 按 hit_count ASC, created_at ASC 排序，淘汰最早的
        evict_count = total - self.max_entries
        candidates = (
            CacheEntry.query
            .order_by(CacheEntry.hit_count.asc(), CacheEntry.created_at.asc())
            .limit(evict_count)
            .all()
        )
        ids_to_remove = [c.id for c in candidates]
        self._rebuild_index_without(ids_to_remove)
        for c in candidates:
            db.session.delete(c)
        db.session.commit()
```

### 2.2 LLM Function Calling

#### 2.2.1 当前项目的问题

当前项目的 `llmFullAnalysis` 函数（`index.html` 行 4407）使用**纯文本 Prompt** 让 LLM 输出 JSON，然后通过**正则表达式**从 LLM 的文本响应中提取 JSON：

```javascript
// 当前实现（行 4450-4469）— 脆弱的 JSON 提取方式
var res = await fetch(baseUrl + '/v1/chat/completions', {
  // ...
  body: JSON.stringify({
    model: cfg.model || preset.model || 'deepseek-chat',
    temperature: 0,
    max_tokens: 512,
    messages: [
      {role:'system', content:'你是数据分析专家。根据数据画像和用户问题，输出精确的查询方案JSON。只输出JSON，不要任何多余文字。'},
      {role:'user', content: prompt}  // prompt 中用自然语言描述 JSON Schema
    ]
  })
});
var data = await res.json();
var content = data.choices[0].message.content;
var m = content.match(/\{[\s\S]*\}/);  // ★ 正则提取 JSON，容易出错
if (!m) return null;
var result = JSON.parse(m[0]);  // ★ 直接 JSON.parse，无容错
```

**存在的问题**：

1. **LLM 可能输出非纯 JSON**：即使 Prompt 要求"只输出 JSON"，LLM 仍可能输出 ```` ```json ... ``` ```` 包裹的内容，或附带解释文字，导致正则提取失败。
2. **无字段校验**：`JSON.parse` 成功不代表字段合法，`dimension` 可能是空字符串、`aggregation` 可能是拼写错误的 `"averge"`。
3. **无枚举约束**：`intent` 应该是 `ranking|trend|comparison|...` 之一，但 LLM 可能输出 `"排序"` 或 `"rank"`。
4. **错误处理粗糙**：正则匹配失败直接返回 `null`，用户看到的是"无法分析"，无法定位原因。

#### 2.2.2 改造方案：使用 Function Calling

Function Calling 是 OpenAI 兼容 API 的原生能力，允许开发者定义一个函数 Schema，LLM 会严格按照 Schema 输出结构化参数，而非自由文本。改造后的核心优势：

| 维度 | 纯文本 Prompt（当前） | Function Calling（改造后） |
|------|---------------------|--------------------------|
| **输出格式** | LLM 自由输出文本，需正则提取 JSON | LLM 原生输出结构化 `function_call.arguments`（JSON 格式保证） |
| **字段校验** | 无，`JSON.parse` 后不校验 | API 层面强制 Schema 约束，字段类型/枚举值自动校验 |
| **枚举约束** | 靠 Prompt 文字提示，LLM 可能不遵守 | `enum` 参数强制 LLM 只能输出指定值 |
| **必填字段** | 无法强制 | `required` 参数指定必填字段，缺失时 API 返回错误 |
| **错误处理** | 正则失败返回 null | `function_call` 不存在或参数不全时有明确错误信息 |
| **Token 效率** | Prompt 中需用大量文字描述 JSON Schema | Schema 作为 `functions` 参数传入，不占用 user message 的 Token |

#### 2.2.3 完整的 Function Calling Schema 定义

```python
# backend/llm/function_schema.py
"""
LLM Function Calling Schema 定义
对应当前项目 llmFullAnalysis（行 4407）的 13 条规则 + JSON Schema
改造后通过 Function Calling 原生约束 LLM 输出
"""

QUERY_ANALYSIS_FUNCTION = {
    "name": "analyze_data_question",
    "description": (
```

#### 2.2.4 Function Calling 调用与解析

```python
# backend/llm/llm_client.py
"""
LLM 客户端：封装 OpenAI 兼容 API 的 Function Calling 调用
替代当前项目 index.html 行 4407-4489 的 llmFullAnalysis 函数
"""
import json
import os
import time
import httpx
from typing import Optional, Dict, Any

from .function_schema import QUERY_ANALYSIS_FUNCTION, build_llm_messages


class LLMClient:
    """统一的 LLM 调用客户端，支持 OpenAI / DeepSeek 等兼容 API"""

    def __init__(self):
        self.api_base = os.getenv("LLM_API_BASE", "https://api.deepseek.com")
        self.api_key = os.getenv("LLM_API_KEY", "")
        self.model = os.getenv("LLM_MODEL", "deepseek-chat")
        self.temperature = float(os.getenv("LLM_TEMPERATURE", "0"))
        self.max_tokens = int(os.getenv("LLM_MAX_TOKENS", "512"))
        self.timeout = int(os.getenv("LLM_TIMEOUT", "30"))

    async def analyze_question(
        self, question: str, data_profile: str
    ) -> Optional[Dict[str, Any]]:
        """
        使用 Function Calling 分析用户问题，返回结构化查询方案。
        对应原前端 llmFullAnalysis(question, dataProfile) 函数。

        Args:
            question: 用户自然语言问题
            data_profile: 数据画像文本（由 build_data_profile 生成）

        Returns:
            查询方案字典，包含 dimension, metric, aggregation, filters 等；
            失败时返回 None。
        """
        messages = build_llm_messages(question, data_profile)

        payload = {
            "model": self.model,
            "temperature": self.temperature,
            "max_tokens": self.max_tokens,
            "messages": messages,
            "functions": [QUERY_ANALYSIS_FUNCTION],
            "function_call": {"name": "analyze_data_question"},
        }

        headers = {
            "Content-Type": "application/json",
            "Authorization": f"Bearer {self.api_key}",
        }

        try:
            start = time.time()
            async with httpx.AsyncClient(timeout=self.timeout) as client:
                resp = await client.post(
                    f"{self.api_base}/v1/chat/completions",
                    json=payload,
                    headers=headers,
                )
                resp.raise_for_status()

            data = resp.json()
            elapsed_ms = int((time.time() - start) * 1000)

            # Function Calling 结果在 choices[0].message.function_call 中
            message = data["choices"][0]["message"]

            if "function_call" not in message:
                # LLM 未调用函数，尝试从 content 中提取（降级兼容）
                content = message.get("content", "")
                return self._fallback_parse(content)

            func_call = message["function_call"]
            arguments = json.loads(func_call["arguments"])

            # 字段校验与补全
            arguments = self._validate_and_fix(arguments)

            print(f"[LLM] 分析完成，耗时 {elapsed_ms}ms，意图: {arguments.get('intent')}")
            return arguments

        except httpx.TimeoutException:
            print(f"[LLM] 请求超时（{self.timeout}s）")
            return None
        except json.JSONDecodeError as e:
            print(f"[LLM] JSON 解析失败: {e}")
            return None
        except Exception as e:
            print(f"[LLM] 调用失败: {e}")
            return None

    def _validate_and_fix(self, result: Dict[str, Any]) -> Dict[str, Any]:
        """对 LLM 返回的查询方案进行字段校验与修正"""
        # 确保必填字段存在
        required = ["dimension", "metric", "aggregation", "intent", "chartType"]
        for field in required:
            if field not in result:
                result[field] = None if field in ("dimension", "metric") else ""

        # 枚举值校验
        valid_aggregations = ["sum", "avg", "count", "max", "min", "ratio"]
        if result["aggregation"] not in valid_aggregations:
            result["aggregation"] = "sum"  # 降级为 sum

        valid_intents = ["ranking", "trend", "comparison", "distribution",
                         "summary", "list", "correlation", "filter"]
        if result["intent"] not in valid_intents:
            result["intent"] = "summary"  # 降级为 summary

        valid_charts = ["bar", "line", "pie", "scatter", "table", "number"]
        if result["chartType"] not in valid_charts:
            result["chartType"] = "bar"  # 降级为 bar

        # limit 默认值
        if not result.get("limit"):
            result["limit"] = 10

        # filters 默认空数组
        if not result.get("filters"):
            result["filters"] = []

        return result

    def _fallback_parse(self, content: str) -> Optional[Dict[str, Any]]:
        """降级方案：当 LLM 未调用 function_call 时，从文本中提取 JSON"""
        import re
        match = re.search(r'\{[\s\S]*\}', content)
        if not match:
            return None
        try:
            result = json.loads(match.group())
            return self._validate_and_fix(result)
        except json.JSONDecodeError:
            return None


# 全局单例
llm_client = LLMClient()
```

#### 2.2.5 对比纯正则规则的优势

| 维度 | 正则规则（当前 `classifyIntent`） | Function Calling（改造后） |
|------|----------------------------------|--------------------------|
| **覆盖率** | 仅覆盖预定义的正则模式，新问法需手动添加规则 | LLM 理解自然语言语义，覆盖任意表达方式 |
| **维护成本** | 每种新问法需修改 `classifyIntent`（行 4642）的 if-else 链 | 无需修改代码，LLM 自动理解新问法 |
| **准确率** | ~70%（复杂/未见过的问法频繁失败） | 90%+（LLM 语义理解 + Schema 约束） |
| **字段映射** | `parseDimension`/`parseMetric` 靠模糊字符串匹配 | LLM 直接从数据画像中选择正确列名 |
| **多义性处理** | 正则无法区分"平均薪资"中的"平均"是聚合方式还是修饰词 | LLM 理解上下文语义，准确判断 |
| **复合查询** | 多条件组合需大量全局状态变量（`window._xxx`） | LLM 一次性输出完整查询方案，无状态污染 |
| **可测试性** | 正则逻辑与 UI/SQL/图表高度耦合，无法独立测试 | Function Calling 输出为纯 JSON，可独立单元测试 |
| **可扩展性** | 新增意图需改正则 + 改 SQL 生成 + 改图表渲染 | 只需在 Schema 中新增字段，LLM 自动适配 |

### 2.3 Flask 后端

#### 2.3.1 为什么不用 Django

| 维度 | Flask | Django |
|------|-------|--------|
| **设计哲学** | 微框架，只提供路由 + 请求/响应处理，其他自由组合 | 全功能框架，内置 ORM / Admin / Auth / Forms / Middleware |
| **学习曲线** | 平缓，核心概念少（route / request / response） | 陡峭，需理解 settings / apps / middleware / ORM / admin 等 |
| **灵活性** | 高，自由选择 ORM（SQLAlchemy）、数据库、缓存方案 | 中，Django ORM 与框架深度耦合，替换成本高 |
| **项目规模适配** | 中小型 API 服务，本项目的 API 端点 < 10 个 | 大型全功能 Web 应用（含后台管理、用户系统、表单等） |
| **启动速度** | 5 行代码即可启动一个 API 服务 | 需 `django-admin startproject` + 配置 settings.py |
| **学习价值** | 理解 WSGI 协议、请求生命周期、中间件原理 | 理解大型框架的设计模式和约定优于配置 |
| **对本项目的适配** | 本项目是 API 服务，不需要 Admin 后台、模板渲染、表单验证 | Django 的大部分内置功能用不上，引入不必要的复杂度 |

**核心决策依据**：

1. **够用就好**：本项目的后端职责是接收 API 请求、调用 LLM、执行 SQL、返回 JSON。Flask 的路由 + jsonify 完全满足需求，Django 的 Admin / Forms / Templates / Auth 均不需要。
2. **学习价值**：Flask 让开发者直接接触 WSGI 协议和请求处理链路，理解 Web 框架的底层原理。Django 封装了大量细节，"魔法"过多，不利于深入理解。
3. **渐进式引入**：Flask 可以从单文件 `app.py` 起步，逐步拆分为蓝图（Blueprint）和模块。Django 需要从一开始就遵循其项目结构约定。
4. **生态兼容**：Flask 与 SQLAlchemy、FAISS、Pandas 等数据处理库的集成更自然，无需适配 Django 的组件体系。

```
backend/

├── wsgi.py                             # Gunicorn WSGI 入口（生产部署用）
│
├── api/                                # API 路由层（Flask Blueprints）
│   ├── __init__.py                     # 蓝图注册汇总
│   ├── upload.py                       # POST /api/upload — 文件上传与解析
│   ├── query.py                        # POST /api/query — 自然语言查询（核心端点）
│   ├── insight.py                      # POST /api/insight — 数据集整体洞察
│   ├── history.py                      # GET /api/history — 查询历史列表
│   ├── schema.py                       # GET /api/schema — 获取数据 schema
│   ├── cache.py                        # GET /api/cache/stats + DELETE /api/cache/clear
│   ├── dataset.py                      # DELETE /api/dataset/{id} — 删除数据集
│   └── errors.py                       # 统一错误处理器注册
│
├── services/                           # 业务逻辑层
│   ├── __init__.py
│   ├── query_processor.py              # 查询编排器：缓存检查→LLM→SQL→执行→洞察→缓存写入
│   ├── sql_generator.py                # SQL 生成器：查询方案JSON → 标准SQL语句
│   ├── sql_executor.py                 # SQL 执行器：安全校验 + SQLite 执行 + 结果格式化
```

```python
# backend/models/dataset.py
"""Dataset 模型 — 数据集元信息"""
import json
from datetime import datetime, timezone
from .database import db


class Dataset(db.Model):
    __tablename__ = "datasets"

    id = db.Column(db.String(64), primary_key=True)
    # 存储到磁盘的文件名（带 dataset_id 前缀，避免冲突）
    filename = db.Column(db.String(256), nullable=False)
    # 用户上传时的原始文件名
    original_name = db.Column(db.String(256), nullable=False)
    # 文件大小（字节）
    file_size = db.Column(db.Integer, nullable=False)
    # 数据行数
    row_count = db.Column(db.Integer, nullable=False)
    # 列名列表的 JSON 字符串
    # 例: '["菜品名称", "分类", "价格", "销量", "评分", "上架日期"]'
    columns_json = db.Column(db.Text, nullable=False)
    # 字段信息数组的 JSON 字符串
    # 例: '[{"name":"价格","type":"currency","null_rate":"0.0%","sample":"38"}, ...]'
    field_info_json = db.Column(db.Text, nullable=False)
    # 创建时间（UTC）
    created_at = db.Column(
        db.DateTime, default=lambda: datetime.now(timezone.utc), nullable=False
    )

    # 关系：一个数据集有多条查询历史
    query_history = db.relationship(
        "QueryHistory",
        backref="dataset",
        cascade="all, delete-orphan",
        lazy="dynamic"
    )
    # 关系：一个数据集有多条缓存条目
    cache_entries = db.relationship(
        "CacheEntry",
        backref="dataset",
        cascade="all, delete-orphan",
        lazy="dynamic"
    )

    def get_columns(self) -> list:
        """解析 columns_json 返回列名列表"""
        return json.loads(self.columns_json) if self.columns_json else []

    def get_field_info(self) -> list:
        """解析 field_info_json 返回字段信息列表"""
        return json.loads(self.field_info_json) if self.field_info_json else []

    def to_dict(self) -> dict:
        """序列化为字典（用于 API 响应）"""
        return {
            "dataset_id": self.id,
            "filename": self.filename,
            "original_name": self.original_name,
            "file_size": self.file_size,
            "row_count": self.row_count,
            "columns": self.get_columns(),
            "field_info": self.get_field_info(),
            "created_at": self.created_at.isoformat() if self.created_at else None,
        }
```

```python
# backend/models/cache_entry.py
"""CacheEntry 模型 — 语义缓存条目"""
import json
import struct
from datetime import datetime, timezone
from .database import db


class CacheEntry(db.Model):
    __tablename__ = "cache_entries"

    id = db.Column(db.String(64), primary_key=True)
    # 外键关联 Dataset
    dataset_id = db.Column(
        db.String(64), db.ForeignKey("datasets.id"), nullable=False, index=True
    )
    # 用户原始问题（用于精确匹配 L1 缓存）
    question = db.Column(db.Text, nullable=False)
    # 问题的 MD5 哈希（用于精确匹配快速查找，加索引）
    question_hash = db.Column(db.String(32), nullable=False, index=True)
    # 问题向量（384维 float32 的二进制 BLOB）
    # 存储方式: struct.pack(f"{384}f", *vector) → bytes (1536 bytes)
    question_vector = db.Column(db.LargeBinary, nullable=False)
    # 缓存的 SQL 语句
    sql_text = db.Column(db.Text, nullable=False)
    # 缓存的查询结果 JSON
    result_json = db.Column(db.Text, nullable=True)
    # 缓存的图表配置 JSON
    chart_config_json = db.Column(db.Text, nullable=True)
    # 缓存的洞察文字
    insight = db.Column(db.Text, nullable=True)
    # 命中时的相似度分数（记录最近一次命中的相似度）
    similarity_score = db.Column(db.Float, nullable=True)
    # 命中次数（用于 LRU 淘汰策略）
    hit_count = db.Column(db.Integer, default=0, nullable=False)
    # 创建时间
    created_at = db.Column(
        db.DateTime, default=lambda: datetime.now(timezone.utc), nullable=False
    )
    # 最后一次命中时间（用于 LRU 淘汰策略）
    last_hit_at = db.Column(
        db.DateTime, default=lambda: datetime.now(timezone.utc), nullable=False
    )

    # 向量维度常量
    VECTOR_DIM = 384

    @classmethod
    def encode_vector(cls, vector: list) -> bytes:
        """将 float 列表编码为二进制 BLOB（节省存储空间）"""
        return struct.pack(f"{cls.VECTOR_DIM}f", *vector)

    @classmethod
    def decode_vector(cls, blob: bytes) -> list:
        """将二进制 BLOB 解码为 float 列表"""
        return list(struct.unpack(f"{cls.VECTOR_DIM}f", blob))

    def get_vector(self) -> list:
        """获取问题向量（解码后）"""
        return self.decode_vector(self.question_vector)

    def get_result(self) -> dict:
        return json.loads(self.result_json) if self.result_json else None

    def get_chart_config(self) -> dict:
        return json.loads(self.chart_config_json) if self.chart_config_json else None

    def to_cache_result(self) -> dict:
        """序列化为缓存命中结果（用于 API 响应）"""
        return {
            "sql": self.sql_text,
            "data": self.get_result(),
            "chart_config": self.get_chart_config(),
            "insight": self.insight,
            "cached": True,
            "cache_similarity": self.similarity_score,
            "hit_count": self.hit_count,
        }

    def increment_hit(self, similarity: float):
        """增加命中计数并更新最后命中时间"""
        self.hit_count += 1
        self.similarity_score = similarity
        self.last_hit_at = datetime.now(timezone.utc)
```

```sql
    row_count       INTEGER      NOT NULL,
```
