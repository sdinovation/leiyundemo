## 1. 项目概述

**数分精灵**是一个面向非技术用户（运营、市场、业务、HR 等）的智能数据分析工具。用户只需完成两个动作即可获得数据分析结果：

1. **上传数据**：上传 CSV / Excel（`.xlsx` / `.xls`）文件；
2. **自然语言提问**：用中文提出业务问题，例如"各部门的平均薪资是多少"、"2024 年销售额最高的 10 个城市"、"市场份额超过 20% 的品牌有哪些"。

系统会自动完成：意图理解 → 字段映射 → 时间/维度/指标解析 → SQL 生成 → 前端 SQL 执行 → ECharts 可视化 → 文字解读。

### 1.1 当前项目形态

- **交付形式**：纯前端单 HTML 文件应用（`index.html`），约 **773 KB**，包含 **14000+ 行 JavaScript 代码**。
- **集成范围**：UI 渲染、文件解析、字段类型推断、数据画像构建、意图分类、SQL 生成、前端 SQL 执行、图表渲染、LLM 调用（直连 / 飞书代理）、多对话管理全部内联在单文件中。
- **运行方式**：双击 `index.html` 即可在浏览器中运行，无需后端服务器（LLM 能力可选，无 API Key 时走飞书云函数代理）。
- **技术栈**：Tailwind CSS + ECharts + PapaParse + SheetJS（xlsx）+ Lucide 图标 + 原生 JavaScript（无框架、无构建工具）。

### 1.2 目标用户与场景

| 维度 | 说明 |
|------|------|
| 目标用户 | 不会 SQL / Python 的业务人员 |
| 典型数据规模 | 单文件 < 10K 行（受浏览器内存限制） |
| 典型问题类型 | 排名、趋势、对比、分布、汇总、筛选清单、相关性分析 |
| 使用频率 | 一次性 / 临时性分析为主，无长期数据沉淀需求 |

#### 2.2.1 数据上传与解析链

```javascript
// 行 2823 — 文件上传解析入口
function parseCSVFile(file)
```
- **功能**：文件上传的总入口，根据扩展名分流。
- **CSV 分支**：调用 `Papa.parse(file, {...})`，配置 `header: true, dynamicTyping: true, skipEmptyLines: true`，完成后调用 `setParsedData()`。

- **大小限制**：单文件 ≤ 50MB，支持 UTF-8 / GBK 自动识别。

```javascript

function inferFieldInfo(columns, rows)
```
- **功能**：遍历所有列，为每列推断类型。
- **兼容处理**：自动检测 `rows` 是对象格式（`rows[0][col]`）还是数组格式（`rows[0][idx]`）。
- **输出**：`[{ name, type, nullRate, sample }]` 数组。
- **nullRate 计算**：`(总行数 - 非空值数) / 总行数 * 100`，保留 1 位小数 + `%`。

```javascript
// 行 2963 — 推断单个字段类型
function inferFieldType(name, values)
```
- **功能**：基于字段名正则 + 值分布推断字段类型。
- **推断优先级**（从高到低）：
  1. 字段名匹配 → `日期|时间|date|time` → `date`
  2. 字段名匹配 → `金额|价格|销售额|收入|revenue|sales|price|amount|gmv` → `currency`
  3. 字段名匹配 → `率|比例|rate|percent|ratio` → `percent`
  4. 字段名匹配 → `代码|编号|^id$|code|序列号|序号` → `text`（标识符，不作为指标）
  5. 值分布判断：若唯一值比例 > 80% 且字段名不含"量/数/额/价/率/总/均/和/差/比/分"，视为标识符 → `text`
  6. 所有值均为整数 → `int`
  7. 含小数 → `float`
  8. 兜底 → `text`
- **支持的类型枚举**：`date | text | int | float | currency | percent`

```javascript
// 行 4407 — LLM 完整分析（输出查询方案 JSON）
async function llmFullAnalysis(question, dataProfile)
```
- **功能**：规则解析失败时的 LLM 兜底，让 LLM 直接输出结构化查询方案。
- **调用条件**：必须有用户 API Key（`getApiKeyConfig()` 返回非 null 且 `baseUrl` 存在），否则返回 `null`。
- **Prompt 设计**（核心，值得改造时复用）：
  - System：`"你是数据分析专家。根据数据画像和用户问题，输出精确的查询方案JSON。只输出JSON，不要任何多余文字。"`
  - User：包含 `dataProfile` 全文 + 用户问题 + 输出 JSON Schema + 13 条规则
  - `temperature: 0`（确定性输出），`max_tokens: 512`
- **输出 JSON Schema**（改造后端时需对齐）：
  ```json
  {
    "dimension": "分组维度列名，如按整体汇总则填null",
    "metric": "指标列名，问人数/条数填null",
    "secondaryMetric": "第二指标列名或null",
    "allMetrics": ["所有用户提到的指标列名数组"],
    "aggregation": "sum|avg|count|max|min|ratio",
    "isScalar": false,
    "filters": [{"field":"列名","op":"=|>|<|>=|<=","value":"值"}],
    "havingCond": "HAVING条件表达式或null，如AVG(市场份额)>20",
    "sortOrder": "desc|asc|null",
    "limit": 10,
    "intent": "ranking|trend|comparison|distribution|summary|list|correlation|filter",
    "chartType": "bar|line|pie|scatter|table|number",
    "queryUnderstanding": "一句话解释你要怎么分析",
    "ratioColumn": "ratio时的列名",
    "ratioValue": "ratio时的匹配值"
  }
  ```
- **13 条规则要点**（部分）：
  1. 字段名必须使用数据画像中的原始列名，禁止编造
  2. "各XX"/"按XX" → dimension 为对应列
  3. "趋势/变化/增长" → dimension 必须为日期/年份列，chartType 为 line，intent 为 trend
  4. "排名/最高/最低" → sortOrder 为 desc/asc，intent 为 ranking
  5. "占比/分布/比例" → aggregation 为 ratio/count，chartType 为 pie
  6. "XX和YY分别是多少" → allMetrics 列出所有指标，intent 为 comparison
  7. "XX为YY的记录" → filters 添加条件，intent 为 filter
  8. "之间有什么关系" → intent 为 correlation，chartType 为 scatter
  9. "人数/条数/订单数" → aggregation 为 count，metric 为 null
  10. 率/百分比字段做阈值筛选时，HAVING 必须用 AVG 不能用 SUM 或 MAX
  11. aggregation=ratio 时不生成 RATIO() 函数，系统自动用 ROUND 百分比公式
  12. "XX品牌的YY趋势" → dimension 为日期列，filters 添加品牌筛选
  13. 本轮独立判断，不受上轮影响
- **副作用（沉淀学习）**：解析成功后，将 `dimension` 和 `metric` 写入 `loadEdgeStore()` 的 `learnedDims` / `learnedMetrics`，调用 `saveEdgeStore()` 持久化到 localStorage，并调用 `updateTrainingBadge()` 更新 UI 徽章。
- **返回值**：解析后的 JSON 对象，失败时返回 `null`。

#### 2.2.3 核心分析编排链

```javascript
// 行 4584 — 核心分析函数（意图分类 + SQL 生成编排）
async function analyzeQuestion(question)
```
- **功能**：整个分析流程的编排入口，从用户问题到最终结果的全链路调度。
- **状态清理**（行 4585-4598）：函数开头清除上一轮的所有全局状态，避免跨问题污染。清理的状态包括：

  - `window._forceAggregation`、`window._lastHavingCond`、`window._lastMultiConditions`
  - `window._lastRangeFilter`、`window._lastLikeFilter`、`window._diffFields`
  - `window._correlationFields`、`window._countMode`
- **编排流程**：
  1. 调用 `classifyIntent(question, schema)` 进行意图分类
  2. 根据意图调用 `parseTimeRange()` / `parseDimension()` / `parseMetric()` 解析查询要素
  3. 调用 `generateSQL()` 生成 SQL
  4. 前端执行 SQL（基于 `parsedData.rows` 的内存计算）
  5. 调用 `renderChart()` 渲染图表

```javascript
// 行 4642 — 意图分类器
function classifyIntent(userQuestion, schema)
```
- **功能**：基于正则关键词匹配，将用户问题分类为一种意图，并返回 `intent`、`confidence`、`examples`（示例 SQL）。
- **意图枚举**：`ranking | trend | comparison | distribution | summary | list | correlation | filter | diff | recommendation | scalar | groupCount | havingCond | which`
- **核心语义标记**（通过正则检测）：
  - `isRanking`：Top / 排名 / 最高 / 最低 / 最贵 / 最便宜 等（含极值关键词）
  - `isCumulative`：总量 / 累计 / 总计 / 整体 / "所有X的总Y"
  - `isTrend`：趋势 / 走势 / 增长 / 逐月 / 逐年
  - `isCompare`：对比 / vs / 分别 / 差异 / "A和B和C"（3+实体）/ "A、B"
  - `isGroupCount`：各/每/按 + 数量/个数/多少 + 排除"分别是多少"
  - `isDist`：占比 / 比例 / 分布 / 构成 / 份额
  - `isSummary`：总计 / 总共 / 汇总 / "总X支出"
  - `isScalar`：是多少 / 为多少（短问题，排除分组/对比场景）
  - `isRec`：怎么提升 / 如何提高 / 建议 / 策略
  - `isList`：有哪些 / 什么产品 / "是XX的记录"
  - `isFilter`：只看 / 超过 / 低于 / "在...以下"（扩展实体类型列表 30+ 种）
  - `isHavingCond`："平均X超过Y的Z" 模式
  - `isWhich`：哪个 / 哪一种
- **优先级**：从高到低排列，先匹配先返回。优先级顺序（部分）：
  1. 差值（"X和Y的差"）→ `diff`
  2. 建议/策略 → `recommendation`
  3. 相关性分析 → `correlation`
  4. 多条件筛选清单 → `comparison`
  5. 排名/极值 → `ranking`
  6. ...（后续为趋势、分布、对比、汇总、清单、筛选等）
- **副作用**：设置 `window._diffFields`、`window._correlationFields` 等全局状态供后续 `generateSQL` 使用。

```javascript
// 行 7419 — 时间范围解析
function parseTimeRange(q, dateField, rows)
```

- **功能**：从用户问题中解析时间范围，返回 `{ field, minDate, maxDate, days, label }` 或 `null`。

```javascript
// 行 7505 — 维度解析
function parseDimension(q, dimensionFields, columns)
```
- **功能**：从用户问题中解析分组维度字段，返回字段名或 `null`（标量聚合）。
- **核心逻辑**：
  - HAVING 场景：`平均X超过Y的Z` → 从"的Z"提取维度

  - "总...是多少" + 无分组关键词 → `null`
  - 趋势/时间类 → 按日期或年份列分组
  - "哪些X" / "各X" 模式 → 优先返回实体维度（避免被时间维度覆盖）
  - 模糊匹配：字段名包含关系（`f.indexOf(text) >= 0 || text.indexOf(f) >= 0`）

```javascript
// 行 8316 — 指标解析
function parseMetric(q, numericFields, columns)
```
- **功能**：从用户问题中解析指标字段和聚合方式，返回 `{ field, label, ... }` 或特殊标记。
- **特殊返回值**：
  - `{ field: '__COUNT_DISTINCT__', label: '去重计数', countField }`：检测"有多少个不同的X" / "几种X"
  - `{ field: '__COUNT__', label: '计数', countField }`：检测"人数/会员数/条数/个数"等计数模式

```javascript
// 行 8674 — SQL 生成
function generateSQL(timeRange, dimension, metric, aggregation, sortOrder, limit)
```
- **功能**：根据解析出的各要素生成标准 SQL 语句（用于前端执行）。
- **特殊模式**：
  - `metric.field === '__NOOP__'` → 返回 `'-- 文本回复，无需 SQL'`
  - `metric.field === '__DIFF__'` → 生成 `SUM(field1 - field2) AS 差值` 的差值 SQL
  - 多指标模式（`window._lastMultiMetricFields` 长度 ≥ 2）→ 生成联合 SQL，每列独立判断 AVG/SUM
- **SQL 结构**：
  ```sql
  SELECT {dimension}, {AGG(metric) AS metric}
  FROM {tableName}
  WHERE {timeRange条件} AND {extraFilters}
  GROUP BY {dimension}
  HAVING {havingCond}
  ORDER BY {metric} {DESC|ASC}
  LIMIT {limit}
  ```
- **表名生成**：`fileName` 去扩展名 + 非字母数字汉字替换为 `_`。
- **多指标聚合判断**：
  - 率/百分比/ARPU/评分类字段 → `AVG`
  - "平均"紧邻指标名（±5 字）→ `AVG`
  - "总/合计/累计"紧邻指标名 → `SUM`

## 3. 核心瓶颈分析

当前纯前端单文件架构存在以下 8 个核心瓶颈，按严重程度排列：

### 瓶颈 1：正则规则覆盖面有限，复杂/未见过的问法频繁失败

- **现状**：`classifyIntent`、`parseTimeRange`、`parseDimension`、`parseMetric` 等函数高度依赖硬编码正则表达式匹配中文关键词。
- **问题**：
  - 中文表达灵活多变，"各渠道的销售额排名"和"每个渠道卖了多少"语义相同但正则难以统一覆盖。
  - 每遇到一种新问法就需要修改正则，`classifyIntent`（行 4642）已有大量 `// Fix:` 注释，说明反复修补。
  - LLM 仅在规则失败时兜底，而非作为主引擎，导致大量本可由 LLM 准确理解的复杂问题走了脆弱的正则路径。
- **影响**：查询准确率约 70%，用户经常遇到"无法理解"或"理解错误"的情况。

### 瓶颈 2：意图分类逻辑耦合在 14000 行单文件中，难以维护

- **现状**：`classifyIntent`（行 4642）单函数内有数十个正则标记（`isRanking`、`isCumulative`、`isTrend`、`isCompare` 等），优先级硬编码在 if-else 链中。
- **问题**：
  - 新增意图或调整优先级需在巨型函数中小心翼翼地插入条件，容易引入回归。
  - 意图分类、SQL 生成、图表渲染高度耦合，无法独立测试。
  - 14 个全局状态变量（`window._xxx`）在函数间隐式传递，调试困难。
- **影响**：维护成本极高，每次修改都可能引发不可预知的连锁问题。

### 瓶颈 3：无查询缓存，相同问题重复计算，LLM 调用成本高

- **现状**：每次用户提问都走完整的"解析 → SQL → 执行 → 渲染"链路，即使问题完全相同。
- **问题**：
  - LLM 调用（`llmFullAnalysis`）每次都发送完整 Prompt，无语义去重。
  - 相同语义的不同表述（"各部门平均薪资" vs "每个部门的平均工资"）无法复用结果。
  - LLM 调用成本随用户量线性增长。
- **影响**：响应延迟 3-8 秒（LLM 调用），API 费用浪费严重。

### 瓶颈 4：纯前端架构无法持久化数据，刷新即丢失

- **现状**：所有数据存储在浏览器内存（`parsedData`）和 localStorage（LLM 配置、边缘学习）中。
- **问题**：
  - 刷新页面后 `parsedData.rows` 丢失，需重新上传文件。
  - localStorage 有 5-10MB 限制，无法存储大数据集。
  - 无法跨设备访问数据，无法分享分析结果。
  - 对话历史仅存在内存中（`conversations` 数组），关闭即丢失。
- **影响**：用户体验差，无法沉淀分析成果。

### 瓶颈 5：SQL 仅在前端执行，无法支持大规模数据

- **现状**：SQL 执行基于 `parsedData.rows` 的 JavaScript 内存计算（前端 SQL 引擎）。
- **问题**：
  - 浏览器内存限制：单文件 < 10K 行可正常工作，> 50K 行浏览器卡死。
  - 无法利用数据库索引优化，复杂查询（多表 JOIN、子查询）性能差。
  - 无法支持 SQL 高级特性（窗口函数、CTE、HAVING 的完整支持有限）。
- **影响**：数据规模受限，无法满足真实业务场景（通常 100K+ 行）。

### 瓶颈 6：缺乏自动洞察生成，用户需自行解读图表

- **现状**：虽有 `llmDeepInterpretation`（行 4494）和 `enrichInterpretationWithLLM`（行 4556），但仅在查询后被动生成简短解读。
- **问题**：
  - 无主动洞察发现：不会自动扫描数据发现异常、趋势、相关性。
  - 无对比分析：不会自动与历史数据、行业基准对比。
  - 无建议生成：虽有 `recommendation` 意图，但仅走 LLM 文本回复，缺乏数据支撑。
  - 无报告导出：分析结果无法导出为 PDF / 图片 / 分享链接。
- **影响**：用户得到图表后仍需自行解读，"数据分析"的价值未完全发挥。

### 瓶颈 7：无用户系统，无法追踪查询历史

- **现状**：无登录 / 注册 / 用户管理，所有用户共享匿名状态。
- **问题**：
  - 无法追踪用户的查询历史（刷新即丢失）。
  - 无法个性化推荐（基于历史查询推荐相关分析）。
  - 无法做团队协作（共享数据源、分析结果）。
  - 无法做用量统计和成本归因。
- **影响**：产品化程度低，无法商业化运营。

### 瓶颈 8：API Key 管理存在安全隐患

- **现状**：用户 API Key 明文存储在 localStorage（`shufen-api-key-config`），通过 `callLLM` 直接从浏览器发起请求。
- **问题**：
  - API Key 在浏览器中明文存储，任何 XSS 漏洞都可窃取。
  - 直接从浏览器调用 LLM API，Key 暴露在请求头中（Network 面板可见）。
  - `anthropic-dangerous-direct-browser-access: true` header 本身就是危险标记。
  - 无 Key 轮换、无用量限制、无异常检测。
- **影响**：安全合规风险高，企业用户无法接受。

## 5. 改造原则

### 原则 1：渐进式改造 — 不推倒重来

- **保留现有前端 UI 和 ECharts 可视化**：前端界面已打磨成熟，用户体验良好，不重写。
- **保留 `index.html` 作为改造起点**：逐步将前端逻辑迁移到后端 API 调用，前端从"全栈"退化为"纯展示层"。
- **保留 `PROVIDER_PRESETS` 和 `callLLM` 的双格式支持**：迁移到后端 `LLMClient` 抽象层。
- **保留 `llmFullAnalysis` 的 Prompt 设计**（13 条规则 + JSON Schema）：作为后端 LLM 服务的核心 Prompt 模板。
- **改造路径**：前端单文件 → 前端 + 轻量 Flask API → 完整 Flask + LLM + FAISS 平台。

### 原则 2：LLM 优先 — 将 LLM 从兜底提升为主引擎

- **当前**：正则规则为主引擎，LLM 仅在规则失败时兜底。
- **改造后**：LLM 为主引擎（理解意图 + 生成查询方案），正则规则降级为快速路径优化（简单问题走规则、复杂问题走 LLM）。
- **实现**：`classifyIntent` 的正则逻辑保留为"快速匹配层"，命中已知模式时直接返回（省 LLM 调用），未命中时走 LLM。
- **FAISS 缓存层**：LLM 调用前先查 FAISS 语义缓存，相似问题（cosine similarity > 阈值）直接返回缓存结果。

### 原则 3：缓存驱动 — 所有 LLM 调用先查 FAISS 语义缓存

- **语义缓存**：用户问题的 embedding 存入 FAISS，查询时计算相似度，超过阈值的直接返回缓存的查询方案。
- **缓存层次**：
  - L1：精确匹配缓存（问题文本 hash 完全一致）
  - L2：语义匹配缓存（FAISS 向量相似度 > 0.92）
  - L3：LLM 调用（缓存未命中时）
- **缓存失效**：数据源变更时清空该数据源相关的缓存。
- **目标**：缓存命中率 > 60%，显著降低 LLM 调用成本和响应延迟。

### 原则 4：后端承载 — 数据存储、SQL 执行、LLM 调用全部移至后端

- **数据存储**：上传文件持久化到后端（SQLite / DuckDB），不再依赖浏览器内存。
- **SQL 执行**：在后端数据库引擎执行 SQL，支持 100K+ 行，利用索引优化。
- **LLM 调用**：API Key 存储在后端环境变量，前端不接触 Key。
- **API 设计**：RESTful API，前端通过 HTTP 调用后端能力。
- **安全性**：API Key 从前端 localStorage 迁移到后端环境变量，消除安全隐患。

### 原则 5：可展示性 — 每个模块都能独立成为简历技术亮点

- 每个改造模块都应能独立讲解其技术决策、架构设计、解决的工程问题。
- 模块设计应体现技术深度：FAISS 向量检索、语义缓存、LLM 编排、SQL 生成引擎等。
- 每个模块需有可量化的改进效果（性能指标、准确率提升等）。
